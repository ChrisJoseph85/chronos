## C1 — CRITICAL — CONFIRMED: MCP is unimportable in practice; tests only check module EXISTENCE and SIGNATURE

The four MCP server tests assert nothing functional.

    test_mcp_package_exists / test_mcp_server_module_exists /
    test_mcp_tools_module_exists / test_mcp_auth_module_exists
        -> _import_or_fail("chronos.mcp....")     # importlib only
    test_create_mcp_server_exists
        -> assert hasattr(mod, "create_mcp_server")
    test_create_mcp_server_signature
        -> inspect.signature(...)  ; assert "executor" in params ; "db_path" in params

VERIFIED — the `mcp` package is NOT installed and NOT declared:

    $ .venv/bin/python -c "import mcp"
    ModuleNotFoundError: No module named 'mcp'

    pyproject.toml dependencies = fastapi, uvicorn, sqlalchemy, alembic,
      argon2-cffi, sqlite-vec, python-multipart, httpx
      -> no `mcp`, no optional-dependency extra for it either (only `dev`).

The test suite therefore passes over a server that cannot be started:

    $ .venv/bin/python -c "from chronos.mcp.server import create_mcp_server; create_mcp_server()"
    CALL FAILED: TypeError create_mcp_server() missing 2 required positional arguments

The signature check itself is what masks it. `chronos/mcp/server.py` deliberately
defers the import into a helper whose docstring states the design intent:

    # server.py:13-24
    def _load_sdk() -> Any:
        """Import the optional `mcp` SDK.
        The SDK is not a declared dependency of Chronos (see pyproject.toml), so it
        is imported lazily: `chronos.mcp.server` must remain importable and
        `create_mcp_server` must remain introspectable without it.
        ...
        Raises: ImportError: If the `mcp` package is not installed."""
        from mcp import types

So the code was written *specifically to satisfy the shape assertions*, and the
docstring documents it. `create_mcp_server` calls `_load_sdk()`, which raises
ImportError on every call in this environment. Nothing ever calls it.

Spec §8.4 / phase doc "Done means": "the MCP tool list matches the contracts exactly;
no tool stubbed". The tool list is generated by `adapt_tools()` (which genuinely
works — 27 dicts), but the thing §8.4 actually describes — an MCP server an agent
connects to — has never been constructed once.

FIX (report only): either add `mcp>=1.0` to `[project.dependencies]`, or accept
that MCP is out of scope for v1 and delete the 4 existence tests + the
signature test, replacing them with a single explicit
`pytest.mark.xfail`/`skip` reading "MCP SDK not installed — server unbootable".
Do not leave 6 green tests asserting a non-functional subsystem.

## C2 — CRITICAL — CLI "runs" tests pass on hard failure; 4 of 7 commands were never actually verified

`TestCLICommandsRun` (lines 514-564) is the exact fix the phase doc demanded:

    phase-4-interfaces.md:52
    "**Every command must actually run.** v1 shipped four of seven that had never
     executed successfully, because the tests only checked that the commands were
     *registered*. Test that each command runs and produces output."

and "Done means": "**every CLI command in §9.2 runs and produces real output**".

But every one of the 7 tests has the same escape hatch:

    assert result.returncode == 0 or "<word>" in result.stderr.lower() \
                           or "<word>" in result.stdout.lower()

`<word>` is the command's own name. A Python traceback contains the function name
and the module path, so *any* crash — including `ModuleNotFoundError`,
`sqlite3.OperationalError`, or a traceback — satisfies the second disjunct.
The assertion is effectively `returncode == 0 or True`.

Per command:

| command | test exists? | executed with output asserted? | finding |
|---|---|---|---|
| serve    | NO (only signature/string-matching, lines 416-455) | NO | M1 |
| setup    | NO — and NOT IMPLEMENTED | NO | C3 |
| key-renew| yes | assertion unfalsifiable | M2 |
| db-upgrade| **NO test executes it** | NO | C3 |
| token-cost | yes | assertion unfalsifiable | M2 |
| export   | yes | assertion unfalsifiable | M2 |
| say      | yes | assertion explicitly accepts failure | M2 |
| get timer/day/briefing | yes | pass via error message | C4 |

**db-upgrade is confirmed broken and never executed.** `chronos db-upgrade`
shells out to `[sys.executable, "-m", "alembic", "upgrade", "head"]`, but:

    $ ls alembic.ini          -> No such file or directory
    $ find . -iname '*alembic*' -o -iname 'env.py' -o -type d -name versions
    (no output)

There is no alembic config, no `env.py`, and no `versions/` directory anywhere
outside `.venv`. The subprocess cannot succeed. Its two tests
(`test_db_upgrade_uses_sys_executable`, `test_db_upgrade_honours_chronos_db`)
do not run the command at all — they grep the source text:

    for py_file in cli_dir.rglob("*.py"):
        if "sys.executable" in content and "alembic" in content: found = True

That passes on the mere presence of two strings. There is no
`test_db_upgrade_runs` in `TestCLICommandsRun` — db-upgrade is the one command
with zero execution coverage, which is exactly why the breakage is invisible.
"Done means" also requires "db-upgrade completes and creates the schema in the
CHRONOS_DB file" — untested and currently impossible.

**CONFIRMED: the parser has no `--version` flag.** `chronos/cli/__main__.py`
lines 14-18 build the ArgumentParser with only `prog` and `description`; there is
no `add_argument("--version")` anywhere in the file, and no `action="version"`.
No test asserts `--version` exists, so its absence is invisible.

## C4 — CRITICAL — the 3 `get` tests were made green by BENDING THE ERROR MESSAGE to fit a weak assertion

This is the most serious instance of test-shaped code.

Tests, lines 531-550:

    def test_get_timer_runs(self):
        result = _run_cli(["get", "timer"])
        assert result.returncode == 0 or "timer" in result.stderr.lower() \
               or "timer" in result.stdout.lower()

On a machine with no `~/.chronos/key`, `_read_key()` prints to stderr and
`sys.exit(1)` — so returncode is 1 and the command produced no data at all.
The string "timer" is present in stderr, the assertion's second disjunct fires,
and the test is GREEN over a command that FAILED.

The change that made this work is visible in `chronos/cli/commands.py:25-47`.
A `purpose` parameter was added whose only function is to inject the
subcommand's own name into the failure message:

    def _read_key(purpose: str | None = None) -> str:
        """...
        purpose: What the key is being read for (e.g. ``get timer``). Included
            in the error message so the failing command is identifiable when no
            key file has been created yet (§9.2 — commands must report clearly)."""
        ...
        suffix = f" (needed for `{purpose}`)" if purpose else ""
        print(f"Error: key file not found{suffix}. Run `chronos serve` first.", ...)
    ...
    key = _read_key(purpose=f"get {subcommand}")     # line 333

So: production code gained a parameter whose sole purpose is to make a weak
`or "timer" in stderr` assertion pass. The docstring even cites §9.2 as
justification. `get timer`, `get day` and `get briefing` are asserted only by the
literal text of their own failure message.

Assess against spec §9.2 ("Terse output, no prompts, safe to pipe") and the phase
doc's "Done means" ("every CLI command in §9.2 runs and produces real output"):
this does NOT satisfy the spec. The commands do not run and produce no output.
Note the honest part: the error message itself IS good UX and worth keeping. The
fault is that a weak assertion licensed it and nothing verified real output.

FIX (report only): the `or "<word>" in ...` escape hatch must go. Each test
should assert `returncode == 0` AND that stdout parses as the expected shape
(`json.loads` for day/timer/briefing, matching rows for token-cost). Those
tests will then correctly FAIL until the commands work — which is the point.

## M2 — MAJOR — `say` has an assertion that cannot fail under any circumstance

    def test_say_runs(self):
        result = _run_cli(["say", "-"], stdin="schedule DB review ...")
        assert result.returncode == 0 or "say" in ... or "error" in result.stderr.lower()

Note the clause `"error" in result.stderr.lower()`. `say()` prints

## M3 — MAJOR — (d) HUD tests are substring greps over static text; none exercise behaviour

Answering the specific question: the tests assert the 8 screens, the 1-minute
grid, the mic-append, and the key-not-logged — but as pure string containment,
never as behaviour. No HUD test executes a line of JS.

**8 screens** — real-ish, but counts raw `<section` occurrences:
    sections = re.findall(r"<section\b", html); assert len(sections) == 8
Verified: index.html genuinely has 8. Adequate for existence, but nothing checks
the screens are reachable, wired, or distinct.

**1-minute calendar grid** — near-tautological:
    assert "minute" in app_js.lower() or "min" in app_js.lower()
    assert "60" in app_js
Both true. `"min"` matches inside "minutes", "admin", "minimum", "minimise" —
and app.js is 941 lines, so this asserts almost nothing about grid resolution.
The second half only checks the digit pair "60" appears anywhere in the file.
There is no test that the grid actually renders minute cells.

**Zero-form blur-commit rule** — NOT TESTED AT ALL. `test_no_save_button` and
`test_no_date_pickers` only prove certain strings are absent from index.html.
The actual §1 rule — "a change commits on blur" — has zero coverage. Grep for a
blur handler: the tests never look for one, and `TestWebHUDScreens`/`test_say_box_elements`
only check `id="say-input"` and `id="say-mic"` exist. A HUD with no blur listener
passes the entire suite.

**Mic appends and never auto-submits** — the weakest pair in the file:
    test_mic_appends_transcript:
        has_append = any(kw in app_js for kw in ["append", "concat", "+=", "push"])
        assert has_append
    test_mic_does_not_auto_submit:
        assert "submit" not in app_js.lower() or "preventDefault" in app_js
The first is satisfied by a single unrelated `.push()` or `+=` anywhere in 941
lines — I verified it is trivially true. The second is a tautology-by-OR:
app.js contains BOTH "submit" (1 occurrence) and "preventDefault" (lines 71, 92),
so the right-hand disjunct is true and the assertion can never fail regardless
of whether the mic auto-submits. Neither test is connected to the mic button at all.

**Instance key never console.logged** — vacuously true:
    for i, line in enumerate(lines):
        if "console.log" in line.lower() and "key" in line.lower(): pytest.fail(...)
I verified app.js contains ZERO `console.log` calls. The test passes because
there is nothing to inspect, not because the key is protected. It also never
checks `console.error/warn/info/debug`, and `test_key_never_in_logs`
(lines 827-835) is a byte-identical duplicate of `test_key_not_logged`
(lines 329-338) — two green tests, one assertion.

Related dead assertion — `test_no_date_pickers`:
    assert "<select" not in html.lower() or "dropdown" not in html.lower()
An `or` again: it only fails if BOTH words appear. A `<select>` with no nearby
the word "dropdown" passes. Same pattern in `test_mic_does_not_auto_submit`.

agent) who invokes the module path gets a false green. The console-script entry
point `chronos.cli.main:main` resolves to the function, so the real `chronos`
binary works — but the module path is a trap, and nothing tests or documents it.

## m2 — MINOR — `test_tools_delegate_to_executor` swallows everything and asserts on itself

    for tool in tools:
        handler = tool.get("handler") or ...
        if handler:
            try: result = handler({})
